<objective>
Fix UAT Gap 2 (MAJOR, Test 11): photo reorder on the animal edit page does not visibly persist. The user drags a photo, it appears to move, then the UI snaps back to the original order.

Investigation summary (from reading the code; the backend endpoint is fine):
- Backend: `PATCH /animals/:id/photos/reorder` in `backend/src/animals/animals.controller.ts:178` calls `AnimalsService.reorderPhotos(animalId, photoIds)` in `backend/src/animals/animals.service.ts:469`, which loops over `photoIds` and writes `position = i` for each. This works; there is a unit test at `backend/src/animals/animals.service.spec.ts:338` covering it.
- Frontend root cause is in two places:
  1. `frontend/app/components/animals/PhotoUploader.vue:315-349` — the `handlePhotoDrop` branch that deals with reordering existing photos (dragIndex < totalExisting && dropIndex < totalExisting) correctly emits `reorder` with the NEW photoId order, BUT it never mutates the visible list. The component re-renders from `props.photos` (read-only), so after the drop event the UI snaps back to the incoming prop order the moment Vue reconciles.
  2. `frontend/app/pages/org/dashboard/animales/[id]/editar.vue:233-240` — `reorderExistingPhotos` calls PATCH but never updates `animal.value.photos` local order. Even after a successful backend write, the next render shows the server-provided (old) order until a full page reload, because `existingPhotos` is computed from `animal.value.photos` which still has the old `position` values.

Fix strategy: the edit page owns the source of truth. `PhotoUploader` emits the intended new order, the page mutates `animal.value.photos` to match that new order (optimistic), then PATCHes the backend. On failure, revert and toast the error.

Purpose: Users trust what they see. Drag-to-reorder is broken trust — the UI says "done" and then silently discards the change.
Output: A drag-and-drop reorder on the edit page visibly persists, survives a page reload, and matches the database state.
</objective>

    New implementation:

    ```typescript
    async function reorderExistingPhotos(photoIds: string[]) {
      if (!animal.value) return

      // Snapshot the current order so we can revert on failure
      const previousPhotos = [...animal.value.photos]

      // Build a map for O(1) lookup, then rebuild the array in the incoming order.
      // Any photo whose id is not in photoIds (shouldn't happen, but be defensive)
      // is appended at the end in its previous relative order.
      const byId = new Map(previousPhotos.map(p => [p.id, p]))
      const reordered: AnimalPhoto[] = []
      for (const id of photoIds) {
        const photo = byId.get(id)
        if (photo) {
          reordered.push({ ...photo, position: reordered.length })
          byId.delete(id)
        }
      }
      // Append any leftovers (defensive — preserves relative order)
      for (const leftover of previousPhotos) {
        if (byId.has(leftover.id)) {
          reordered.push({ ...leftover, position: reordered.length })
        }
      }

      // Optimistic update — this updates the computed `existingPhotos` and the
      // PhotoUploader re-renders in the new order immediately.
      animal.value.photos = reordered

      try {
        await patch(`/animals/${animalId.value}/photos/reorder`, { photoIds })
        toast.add({ title: t('common.success'), color: 'success' })
      } catch (err: any) {
        // Roll back
        if (animal.value) {
          animal.value.photos = previousPhotos
        }
        toast.add({
          title: t('common.error'),
          description: err?.data?.message || '',
          color: 'error',
        })
      }
    }
    ```

    Key properties:
    - `animal.value.photos = reordered` mutates the source that `existingPhotos` (computed) derives from. The PhotoUploader re-renders in the new order because `props.photos` now reflects it.
    - On failure, `animal.value.photos = previousPhotos` restores the pre-drop order, so the user sees the snap-back and the error toast together — no silent data loss.
    - We do not touch the `PhotoUploader` emit contract (it already emits `reorder` with the correct ID order). The fix lives entirely in the page.

    Do NOT change `removeExistingPhoto`, `setExistingCover`, `saveAnimal`, or `saveNewPhotos` — those already work per UAT Test 11 (which noted "add/remove/cover swap all work"). Leave them exactly as they are.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser (org admin) -> api (PATCH /animals/:id/photos/reorder) | Authenticated user submits a photo-ID ordering |
| api -> database (prisma-rls) | Tenant-scoped update on animal_photos |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-05-01 | Elevation of Privilege | `PATCH /animals/:id/photos/reorder` callable against another org's animal | mitigate | Existing mitigation via `@Roles('ORG_ADMIN')` + PRISMA_RLS: the `animalPhoto.update` runs through the tenant-scoped client, and RLS on `animals` only permits updates where `organization_id = current_setting('app.current_org_id')`. A cross-org caller would see 0 rows updated but no data changes. Already shipped in Phase 2 — this plan does not alter that path. |
| T-02-05-02 | Tampering | Caller sends `photoIds` containing IDs that don't belong to the animal | mitigate | `animalPhoto.update` in a loop updates each photo individually; a photo belonging to a different animal would either be invisible under RLS (no-op) or update someone else's photo's position. To close this, the service could validate membership first, but that requires a schema read per call. **Accept for now**: impact is limited to position field (no URL/key mutation), and photo IDs are UUIDs (unguessable). Ticket filed for a follow-up to add explicit membership validation in a future hardening plan. |
| T-02-05-03 | Information Disclosure | Frontend caches photo IDs in memory | accept | Photo IDs are UUIDs scoped to an authenticated org-admin's own org — no disclosure risk. |
| T-02-05-04 | Denial of Service | Attacker sends a huge `photoIds` array to flood the DB with UPDATEs | mitigate | An animal has at most 10 photos per Phase 2 client-side limit. Add a defensive server-side check: if `photoIds.length > 50` reject with 400. **DEFER to follow-up**: out of scope for this bug fix; tracked for a security hardening plan. |

No new trust boundaries are introduced by this plan; the fix is a frontend state-management bug.
