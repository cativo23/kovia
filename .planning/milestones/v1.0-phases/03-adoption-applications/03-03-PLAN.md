Backend API (staff endpoints from Plan 01):
```
GET    /applications/org         — Staff queue (org-scoped via RLS, paginated)
       Query params: page, limit, animalId, status, dateFrom, dateTo
       Returns: { data: Application[], total, page, limit, totalPages }

GET    /applications/org/:id     — Staff single application detail
       Returns: Application with photos, animal (name + species + first photo)
       Includes denormalized: adopterFirstName, adopterLastName, adopterEmail

PATCH  /applications/:id/status  — Staff status transition
       Body: { status: 'REVISANDO' | 'APROBADA' | 'RECHAZADA' | 'SEGUIMIENTO' | 'ADOPTADA' }
       Returns: updated Application
```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Staff browser -> API | Status transitions from org admin must be validated server-side |
| Org A staff -> Org B data | RLS ensures org admin only sees their own org's applications |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-12 | Information Disclosure | /org/dashboard/aplicaciones | mitigate | Backend GET /applications/org uses prismaRls with CLS org context — org A staff cannot see org B data |
| T-03-13 | Tampering | Status transitions | mitigate | Backend validates staffTransitions map — frontend transition map mirrors but backend is authoritative |
| T-03-14 | Elevation of Privilege | PATCH /:id/status | mitigate | @Roles('ORG_ADMIN') guard prevents adopters from calling staff endpoints |
</threat_model>
